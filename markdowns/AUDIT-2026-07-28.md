## Critical Issues

### C1 — The catalog is a demo fixture, so recommendations do not discriminate

**Description.** `seeds/0002_academic_catalog.sql` seeds **5 colleges, 10 careers, 16 programs, 24 program↔career mappings**. `TOP_N` in [recommendation.ts:113](backend/src/lib/recommendation.ts#L113) is **10**.

**Root cause.** The engine ranks the full catalog and slices the top 10. With exactly 10 careers in the database, the slice is a no-op.

**Impact.** **Every student receives every career in the system.** Two students with opposite RIASEC profiles get identical recommendation lists, differing only in order. A panelist who asks "show me two contrasting students" will see the product's core claim fail live. The same argument applies weakly to programs (top 10 of 16).

Note this is *not* an engine defect — the maths is correct and unit-tested against the hand-computed worked example. The engine is starved of data.

**Recommended fix.** Seed a realistic Philippine catalog: **60+ careers, 40+ programs, 20+ HEIs**, each career with a real `typical_riasec_code`. Careers without a Holland code score a neutral 50 and tie, so code coverage matters more than raw row count. Consider lowering `TOP_N` to 5 for the student-facing view as a secondary safeguard.

**Effort:** 1–2 days (mostly data authoring, not code).

### C2 — Staff password recovery is impossible in production

**Description.** A counselor or admin who forgets their password cannot recover it by any supported route.

**Root cause.** Three facts compose into a dead end:
1. [routes.ts:92](backend/src/modules/identity/routes.ts#L92) returns the reset token **only when `APP_ENV === 'local'`**.
2. `password_reset_tokens` stores only the SHA-256 **hash** — the plaintext is unrecoverable by anyone, including an admin.
3. `updateCounselorSchema` ([schemas.ts:104](backend/src/modules/identity/schemas.ts#L104)) has **no password field and no `must_change_password` field** — there is no admin-initiated reset endpoint.

There is no email channel (documented deviation D7). The UI tells the user "An administrator completes the reset and gives you the reset code" — but no mechanism exists by which an administrator can obtain that code.

**Impact.** Permanent account lockout, recoverable only by a developer running SQL against production D1. On a platform whose only privileged accounts are staff accounts, this is a total loss-of-access risk.

**Recommended fix.** Add `POST /admin/counselors/:id/reset-password` that mints a temporary password through `AuthGuardDO.hash()`, sets `must_change_password = 1`, revokes all tokens, writes an audit row, and returns the plaintext **once** to the admin — mirroring the existing counselor-creation flow, which already does exactly this correctly.

**Effort:** 3–4 hours including tests and the admin UI button.

### C3 — Production environment has never been provisioned or deployed

**Description.** Per `PRODUCTION_REQUIREMENTS.md` (dated 2026-07-25): production DLQs do not exist, **zero migrations are applied** to `CareerLinkAI_Main`, the database is unseeded, and the live `careerlinkai` Worker is running code from 2026-04-25.

**Root cause.** Staging was the working target; production cutover was deferred.

**Impact.** `npm run deploy:production` **hard-fails** at the queue-consumer step. Even if it passed, the app would serve an empty database. `careerlinkai.online` currently serves pre-Phase-A code.

**Additional defect found:** the requirements doc is **stale** — it states "All 13 migrations (0001–0013)" but the repository contains **19** (`0001`–`0019`). Anyone following it as a checklist will under-migrate.

**Recommended fix.** Execute the documented cutover, corrected for 19 migrations:
```bash
npx wrangler queues create careerlinkai-default-dlq
npx wrangler queues create careerlinkai-ai-dlq
npm run db:migrate:production
node scripts/bootstrap-staff.mjs --database CareerLinkAI_Main --env production
# seed catalog (0002) + ai-policy (0003) against production
npm run deploy:production
# then: POST /api/v1/admin/assessment-templates/seed-instruments  (see H1)
```
Add the missing `db:seed:*:production` npm scripts, which do not exist.

**Effort:** 3–5 hours including smoke tests.

### C4 — Recommendation generation has exactly one trigger, and its failures are swallowed

**Description.** `RecommendationService.generateFor()` has **one caller in the entire codebase**: the `AssessmentCompleted` listener in [dispatch-recommendation-generation.ts:62](backend/src/events/dispatch-recommendation-generation.ts#L62). `dispatch()` catches and logs every listener exception by design.

**Root cause.** The swallow is deliberate and correct in isolation — a failing listener must not turn a completed assessment into a 500. But it was never paired with a recovery path. There is **no regeneration endpoint** for students, counselors, or admins.

**Impact.** A transient D1 error, subrequest-budget exhaustion, or a catalog inconsistency during the listener leaves a student with both assessments `SCORED` and **no recommendations, permanently**. The student's screen says "Complete both RIASEC and SCCT to receive them" — advice they have already followed. The only recovery is a counselor resetting an attempt and the student retaking a full 60-item assessment.

This compounds with **C1's sibling issue**: because generation only ever fires on submit, students who complete assessments **before** an admin expands the catalog keep their original recommendations forever. The catalog grows; existing students' recommendations never do.

**Recommended fix.** Add `POST /student/recommendations/regenerate` (self-service, rate-limited) and `POST /counselor/students/:id/recommendations/regenerate`. `generateFor` already replaces a student's set wholesale, so it is safely idempotent — this is a routing and authorization task, not an engine change.

**Effort:** 4–6 hours including tests and a UI button.

## Functional Bugs

### F1 — RIASEC and SCCT cannot be installed from the UI

* **Expected:** an admin installs the two validated instruments through the interface.
* **Actual:** `POST /admin/assessment-templates/seed-instruments` exists and works, but **no frontend code calls it** (verified: zero matches for `seed-instruments` across `frontend/src`). It must be invoked with `curl` plus a hand-copied bearer token.
* **Root cause:** endpoint shipped without its UI affordance.
* **Fix:** add a "Install RIASEC & SCCT" button on the admin Assessments page, visible when neither instrument is present. It is idempotent, so it is safe to expose. **Effort: 1–2 hours.** *(This is also a live production cutover step — without it, a freshly seeded production has no assessments at all.)*

### F2 — Counselors cannot see their students' recommendations

* **Expected:** a counselor reviews a student's recommendations (explicitly in scope, and in `§20`).
* **Actual:** the backend route `GET /counselor/students/:studentId/recommendations` exists, `recommendationApi.getForStudent()` exists, and the hook `useStudentRecommendations()` exists — but the hook has **zero consumers**. No page renders it.
* **Root cause:** the vertical slice was built bottom-up and the top layer was never added.
* **Impact:** the counselor's core professional workflow is unreachable. Ironically, *admins* can see student recommendations (via `CounselorDetailPage`), but the counselor who actually advises the student cannot.
* **Fix:** render the panel in `ClassDetailPage` / a student drawer. All plumbing already exists. **Effort: 3–4 hours.**

### F3 — Career mapping picker silently truncates at 100

* **Expected:** an admin can map a program to any career.
* **Actual:** `catalogApi.listCareers()` requests `per_page: 100` with the comment *"the mapping picker needs the whole catalog in one list"* — but `listCatalogQuerySchema` caps `per_page` at **100** ([schemas.ts:253](backend/src/modules/catalog/schemas.ts#L253)). Beyond 100 careers, the picker silently omits the rest with no indication.
* **Impact:** currently latent (10 careers seeded) but **becomes live the moment C1 is fixed** — the recommended 60+ career catalog is fine, but any real national catalog will exceed 100 and mappings will become quietly impossible. Since program↔career mappings drive `programRiasecCompatibility`, missing mappings degrade recommendation quality invisibly.
* **Fix:** add server-side `search` to `listCatalogQuerySchema` and convert the picker to a typeahead. **Effort: 4–6 hours.**

### F4 — Catalog admin pages have no search

* **Expected:** find a college/career/program in a real catalog.
* **Actual:** `listCatalogQuerySchema` supports only `page` and `per_page` — **no `search`, no filter, no sort**. `CollegeListPage`, `CareerListPage`, `CanonicalProgramPage`, and `KnowledgeListPage` have no search input. (`AuditLogPage`, `AddressPage`, `CounselorManagementPage` and `CounselorDetailPage` *do* — the capability exists in the codebase, just not here.)
* **Impact:** at demo scale, invisible. At production scale, catalog administration becomes unusable — page-by-page through hundreds of rows.
* **Fix:** extend the schema and service with `search`, mirroring the working implementation in `counselor-management-service.ts:131`. **Effort: 4–6 hours.**

### F5 — Deleting a counselor orphans their classes with no reassignment

* **Expected:** deleting a counselor either blocks on, or reassigns, their classes.
* **Actual:** `remove()` ([counselor-management-service.ts:407](backend/src/modules/identity/counselor-management-service.ts#L407)) soft-deletes the user and revokes tokens. It performs **no check on owned classes** and offers no reassignment. Classes keep `counselor_id` pointing at a deleted user.
* **Mitigating factor:** `canViewClass` grants admins access to every class, and `ClassService.list()` returns all classes for admins — so the classes are not lost, and an admin can still administer them.
* **Real impact:** there is **no way to transfer a class to a replacement counselor** — `counselor_id` is set at creation and never writable. In a school where a counselor leaves, their classes can never be owned again.
* **Fix:** block deletion when live classes exist, or add a reassignment step (`PATCH /admin/classes/:id { counselor_id }`). The UI already displays `classes_count` per counselor, so the data for a warning is on screen. **Effort: 4–6 hours.**

### F6 — No error boundary: any render exception blanks the whole app

* **Expected:** a component failure degrades one region.
* **Actual:** zero `ErrorBoundary` / `componentDidCatch` / `errorElement` anywhere in `frontend/src`. A single render-time throw unmounts the entire React tree — white screen, no recovery but a manual reload.
* **Fix:** wrap `AppRoutes` in an error boundary with a reset action; ideally a second one per route group. **Effort: 2 hours.** *(High value before a live defense.)*

## Security Findings

### S1 — No Content-Security-Policy, with a bearer token in `localStorage` — **HIGH**

`public/_headers` sets only `X-Content-Type-Options` and `Referrer-Policy`. **Missing: `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `Strict-Transport-Security`, `Permissions-Policy`.**

The auth token is persisted to `localStorage` ([authStore.ts](frontend/src/stores/authStore.ts) `partialize`), which is readable by any injected script. With no CSP, a single XSS anywhere in the app escalates directly to full account takeover — including admin. Absent `frame-ancestors`, the app is also clickjackable.

**Remediation.** Add to `public/_headers` under `/*` (every header below is safe to also apply to hashed assets, per that file's own accumulation rule):
```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; media-src 'self'; connect-src 'self'; worker-src 'self' blob:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Frame-Options: DENY
Permissions-Policy: geolocation=(), microphone=(), camera=()
```
Verify `worker-src blob:` against pdf.js and `style-src 'unsafe-inline'` against Tailwind before shipping. **Effort: 2–3 hours including verification.**

### S2 — No general API rate limiting — **MEDIUM**

Rate limiting is excellent where it exists (login lockout, join throttle, AI usage, forgot-password) and correctly built on `AuthGuardDO` rather than KV. But **every other authenticated endpoint is unthrottled**. On the Cloudflare Free plan (100k requests/day), one authenticated student looping `/student/assignments` can exhaust the daily quota and take the platform down for everyone.

**Remediation.** A coarse per-user counter (e.g. 300 req/min) as global middleware, reusing the existing `charge()` primitive. Alternatively Cloudflare's WAF rate-limiting rules at the edge, which cost no Worker CPU. **Effort: 3–4 hours.**

### S3 — Uploaded document text is client-supplied and unverified — **LOW**

[routes.ts:54](backend/src/modules/ai/routes.ts#L54) stores the raw file in R2 "for provenance" but ingests `extracted_text` **straight from the request body**. Nothing verifies the text corresponds to the file. An admin could upload an innocuous PDF alongside arbitrary text, which then grounds every AI explanation via RAG.

Mitigated by requiring the **admin** role — the highest-trust actor — so this is a provenance-integrity weakness, not a privilege escalation. File validation is extension-only (no magic-byte check), which is acceptable given the file is never executed or served back.

**Remediation.** Document the trust boundary explicitly; optionally record a hash of both file and text in the audit row so tampering is detectable after the fact. **Effort: 1–2 hours.**

### S4 — Committed seed publishes staff credentials — **LOW (documented, mitigated)**

`seeds/0001_staff_accounts.sql` contains real PBKDF2 hashes for `ChangeMe123`. The file documents the risk at length and `must_change_password = 1` forces rotation at first login; `bootstrap-staff.mjs` is the production path. **Ensure the committed seed is never run against production** — this is already the documented procedure, so the residual risk is process, not code.

### Security controls verified as correct ✅

These were checked and found sound — worth stating explicitly for the defense:

* **PBKDF2 at 600,000 iterations**, correctly chained under the runtime's 100k-per-call ceiling, executed inside a Durable Object for the 30s CPU budget. The iteration count is embedded per-hash, so legacy hashes verify at their own cost. Genuinely sophisticated.
* **Timing-attack resistance**: unknown-email logins verify against a constant dummy hash so they pay identical derivation cost. Constant-time comparison on both the DO hash and the reset-token digest. This is a level of care rarely seen at any level.
* **Lockout counters in a Durable Object, not KV** — with a correct written justification (KV's eventual consistency and write quota disqualify it as a security counter).
* **Atomic check-and-charge** (`charge()`) closes the TOCTOU that a `check()`-then-record pair would open.
* **SQL injection**: not possible. All queries go through Drizzle; every `sql` template interpolation binds parameters.
* **XSS**: no `dangerouslySetInnerHTML`, no `innerHTML`, no `eval` anywhere.
* **IDOR**: student routes resolve "me" from the token — **no student id appears in any student-scoped URL**, so parameter tampering has nothing to tamper with. Counselor cross-student access returns **404, not 403**, correctly refusing to confirm existence.
* **Session invalidation**: `authenticate` re-checks `status` and `deletedAt` on every request, so suspension takes effect immediately rather than at token expiry.
* **Password rotation** revokes all tokens; expired tokens are deleted on presentation.

## Performance Findings

### P1 — 3.26 MB logo shipped on every page — **HIGH**

```
careerlinkai_logo-B6U3_N8l.png   3,263.55 kB
careerlinkai_art-_GSHsoyu.png    1,055.42 kB
index-CboRDc_S.js                  932.07 kB │ gzip: 272.59 kB
lib-89UJpjLH.js                    497.25 kB │ gzip: 125.45 kB
```

**`frontend/assets/optimized/` already contains the correctly-sized variants** — `careerlinkai_logo-256.png` at **14 kB** and `-256.webp` at 18 kB — but **nothing imports them**. [Logo.tsx:2](frontend/src/components/brand/Logo.tsx#L2) imports the full 3.26 MB original, and `Logo` renders in every layout header.

A further 3.26 MB copy sits at `public/logo.png`, and `src/assets/careerlinkai_logovideo.mp4` (2 MB) is unreferenced.

**Impact.** Initial load is roughly **5.2 MB** for the login screen. On a mid-tier Philippine mobile connection that is 15–30 seconds to first meaningful paint. For a platform whose users are SHS students on phones, this is the single most visible quality problem in the product.

**Fix.** Point `Logo.tsx` at `careerlinkai_logo-256.webp`; use `<picture>` with the PNG fallback; replace `public/logo.png` with a properly sized favicon/OG image; delete the unreferenced `.mp4` and the duplicate root `assets/` tree. **Effort: 1–2 hours for a ~99% reduction in image weight.** Highest value-per-hour fix in this report.

### P2 — No code splitting — **MEDIUM**

Every route is a static import in [router.tsx](frontend/src/routes/router.tsx); there is no `React.lazy` or `Suspense` anywhere. The result is one **932 kB (273 kB gzipped)** chunk containing every admin, counselor, and student page. A student who will never open the assessment builder still downloads it, including the pdf.js integration.

**Fix.** `React.lazy` per route group (admin / counselor / student / public), wrapped in `Suspense` with the existing loading spinner. Expect a 60–70% cut in student-path JavaScript. **Effort: 3–4 hours.**

### P3 — Backend query patterns are good ✅

Explicitly checked and found sound: `DashboardService` runs 3 queries with no N+1; `hydrateResultViews` uses a fixed query count independent of row count (documented as fix C1 in their notes); `footprintsFor` batches counts; `chunkForInsert` derives width from the schema so D1's 100-parameter ceiling cannot rot. Transaction handling via `db.batch()` is the correct pattern for D1's lack of interactive transactions, and the atomic submit (folding the status transition into the scoring batch) is a genuinely good piece of design.

## Backend Improvements

**Refactoring.**
* `assessment-builder-service.ts` is **1,644 lines** and `assessment-attempt-service.ts` **1,446** — both are doing several jobs. Splitting question authoring, version lifecycle, and assignment into separate services would help maintainability. Not urgent; the internal structure is clean.
* `ForgotPasswordPage` and `ResetPasswordPage` call `httpClient` directly, violating the codebase's own stated component → hook → service rule (asserted in `authApi.ts`'s header). Move them into `authApi`.

**API.** Add `search`/`sort` to catalog list schemas (F4); add regeneration endpoints (C4); add admin password reset (C2).

**Database.** The schema is strong — 132 indexes across 45 tables, partial unique indexes correctly scoped with `WHERE deleted_at IS NULL` so soft-deleted rows do not block reuse of a slug, and a sensible cascade split (35 `cascade` / 15 `set null`). Fourteen FKs omit `onDelete`, defaulting to `NO ACTION`; for creator/author references that is the safe choice, but it should be an explicit `restrict` for readability.

**Dead code to remove.** `frontend/src/index1.css` (unreferenced), the duplicate root `frontend/assets/` tree, `careerlinkai_logovideo.mp4`, and `useStudentRecommendations` (once F2 lands, it becomes live instead).

## Final Verdict

New seed **`backend/seeds/0004_academic_catalog_expansion.sql`**, generated deterministically
(UUIDv5 from each row's natural key, so it is byte-stable and `INSERT OR IGNORE` is genuinely
idempotent).

|---|---|---|
| Colleges | 5 | **20** |
| Careers | 10 | **68** |
| Canonical programs | — | **48** |
| Program offerings | 16 | **309** |
| Program↔career mappings | 24 | **933** |

Sourced as requested: programs use **CHED priority degree programme** names, careers sit inside
**PSOC 2012** major groups (chiefly Professionals and Technicians and Associate Professionals), and
the institutions are real Philippine HEIs with programmes drawn from what each actually offers.
Salary bands and Holland codes are labelled in the file itself as *considered estimates, not
measurements* — they are seed values an administrator edits, and nothing presents them to a student

**Verified** against a real SQLite database with all 19 migrations applied: 0 foreign-key

### C2 — Staff password recovery now exists ✅

`POST /admin/counselors/{id}/reset-password` — generates a temporary password through
`AuthGuardDO.hash()`, returns the plaintext exactly once, sets `must_change_password`, revokes every
session, clears **both** the login lockout and the forgot-password throttle, deletes any pending
reset token, and writes a new `COUNSELOR_PASSWORD_RESET` audit action.

UI: a confirmed **Reset password** action per row on the admin Counselors page, reusing the existing
"shown only once" banner.

**9 new tests** (`test/auth/counselor-password-reset.test.ts`), all passing — including that the
issued password *actually signs in* (this project has twice shipped a password an API claimed
worked and did not), that the old one stops working, that all sessions die, that an **active
lockout is cleared** (without which the reset is useless for the 15 minutes it matters most), that
a second reset supersedes the first, and that the plaintext never appears in the audit trail.

### C4 — Recommendation regeneration ✅

`POST /student/recommendations/regenerate` and
`POST /counselor/students/{id}/recommendations/regenerate`. Throttled at 5 per 10 minutes on a new
`AuthGuardDO` counter keyed on the **student**, not the caller — so a counselor working a roster is
not throttled after five students, and a student cannot dodge their own limit via staff.

UI: "Rebuild my recommendations" in the empty state, plus a quiet "Rebuild" in the header when a set
exists (the stale-catalog case). The empty-state copy no longer tells a student who has finished
both assessments to go and finish them.

**12 new tests** (`test/recommendation/regeneration.test.ts`), all passing. They delete a student's
recommendation rows directly — reproducing the exact swallowed-listener failure — and assert
recovery. Also covered: idempotency, the 404-not-403 rule on the counselor route, `200 + null` for a
student who genuinely has one instrument left, the throttle, and that a career added *after*
assessment appears on rebuild.

### F1 — RIASEC/SCCT installable from the UI ✅

"Install RIASEC & SCCT" button on the admin Assessments page, gated on the signed-in user's **role**
rather than the route (an admin in the counselor shell is still an admin). Always offered, since the
call is idempotent and "not on this filtered page" is not evidence of absence.
